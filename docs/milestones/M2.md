## How the subsystems were integrated

Routes obtain services through `app/api/dependencies.py`. The providers build each repository from its path in `app/core/config.py` and pass repositories/services to the service that needs them. FastAPI shares dependencies within a request. Routes handle HTTP models; services enforce rules; repositories alone read and write JSON.

For `POST /checkout`, the request travels through:

1. `get_current_customer`: verify the token and load the active caller.
2. Checkout route → `CheckoutService.checkout` → `prepare`: load the customer, active cart and restaurant, validate quantities and ask `MenuService.get_orderable_item` to recheck the menu.
3. `price_lines`: calculate the current lines and total using Decimal rounding.
4. `OrderRepository.create`: save the order snapshot to `orders.json`.
5. `CartService.mark_checked_out` → `CartRepository`: close the source cart in `carts.json`.
6. Return the `Order` response. `OrderService` later reads the same saved snapshot for the authenticated owner.

| File | Stored records and relationships |
| --- | --- |
| `restaurants.json` | Restaurants with stable identifiers. |
| `menu_items.json` | Menu items linked to `restaurant_id`. |
| `customers.json` | Profiles, role/active state and salted password hashes. |
| `carts.json` | Customer/restaurant identifiers, item identifiers and quantities, plus active/checked-out state. No stored prices. |
| `orders.json` | Customer, restaurant and source-cart identifiers, immutable line/address snapshots and totals. |

The committed examples give Ben a historical order and a filled cart; Chloe retains a historical order after account deactivation; Ana starts with no cart history. `test_representative_data_has_valid_relationships_and_totals` validates the five-file relationships. Ordinary API tests use empty cart/order history in temporary files; the seeded demo test explicitly copies the representative history.

Use the setup in the [README](../../README.md). Run on a fresh temporary copy of **all five** data files, with a stable `SECRET_KEY`, so restarting preserves tokens and the committed examples remain unchanged. Keep that directory and key for every restart in this demo. Serve the frontend on port 5500 and the API on port 8000. ## Known limitations

- JSON files provide atomic replacement of an individual file, but no cross-file transaction or locking for concurrent requests. Saving an order and closing its cart are separate writes; checkout has recovery logic for a saved order whose cart was not closed.
- Total equals subtotal. There is no payment processing, delivery fee, tax calculation or order progression beyond `placed`.
- The backend rechecks item availability/prices at checkout. A hand-edited cart whose stored restaurant disagrees with an item's restaurant still needs the final #51 business-rule audit/fix; API cart additions already reject mixed restaurants.
- Tokens expire and a newly generated signing key invalidates old tokens. Set `SECRET_KEY` to keep them valid across restarts. There is no refresh-token or password-reset workflow.
- Browser/API integration is limited to the configured localhost/127.0.0.1 port-5500 origins. Frontend implementation and browser verification are present on the review branches; #90/#91 still need approvals and merging.
